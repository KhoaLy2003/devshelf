## Observations (not failures)

- Item positions are stored 0-based in `workspace_items.position`; the UI numbers items from 1 (AC-10 holds).
- The list is ordered by name (Empty one before Ops Runbooks).
- Duplicate message for the trailing-backslash case shows the normalised path (no trailing backslash); the upper-case case shows the path as typed.
- Persistence checks use WebView reload and DB reads; no full restart of devshelf.exe was done.
- The native-dialog automation had a slow start (hung UIA ValuePattern script, stale "Open" and "Rename" `#32770` windows; closed). It does not indicate an app defect.
- Restart persistence (AC-20 across a real devshelf.exe restart): NOT RUN. The app was never relaunched after the final cleanup; the later "exit code 127" on the dev-server job is the supervisor reporting the job after devshelf.exe was force-stopped at cleanup, not a failed relaunch. W18 and W20 are therefore PASS for reload plus DB read only.
- Browse baseline: before the first successful Browse + Add, the item count for the workspace was 0 (W13 check). Several stacked dialog attempts happened before it; the path field was filled once by the late-completing dialog, and the item appeared only after the "Add item" button was clicked in the dialog (DB count 0 -> 1, position 0, no duplicates).
- Copy observation: the detail header reads "N items, reopened in this order." It describes reopen behaviour that belongs to F05 (Restore is not built). Not part of the AC-10 check and not counted as a failure; flagged for review.
- Live DB is now migrated to user_version 4; `devshelf.sqlite3.f03-backup` is the pre-F04 (version 3) restore point.
